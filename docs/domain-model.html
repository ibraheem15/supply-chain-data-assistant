Canonical class and dependency diagram for what is actually implemented in src/. Kept in sync with domain-model.md.

Planned (not yet implemented) design lives in research.md, technical-design-doc.html, and business-pitch.html. This page shows only what exists in code today.

Current State: Phase 1 Only

The only package that exists is src/data/, containing a single module: ingest_supply_chain_dataset.py. It has one class-shaped concept (a Value Object), one domain exception, and module-level functions that orchestrate validation and publishing. There is no resources/ application layer, agent, or tool interface yet — those are Phase 3 work.

Dependency Diagram

parse_csv() has no dependency on the database — it can be reasoned about, and tested, with SQL Server never running. Only load_config() and publish_records() depend on pyodbc and the environment file.

DDD Concepts Applied Here

ConceptWhere
Ubiquitous LanguageCOLUMNS — business-readable field names (iot_temperature, risk_classification) used everywhere except the one translation point below
Anti-Corruption LayerLEGACY_COLUMN_NAMES — the single place mapping ubiquitous language to the legacy system's terse column names (IOT_TEMP_C)
Entity vs. Value ObjectDatabaseConfig is a Value Object: no identity, immutable, defined only by its field values. No Entities yet — Phase 3's structured-data path will likely introduce one
Interface as ContractIngestionError is the contract for "expected, actionable failure" vs. an unexpected bug
Dependency directionValidation logic (parse_csv) depends on nothing infrastructure-related; only the database-facing functions depend on pyodbc
Packages as layersNot yet meaningful with a single module — see below for what Phase 3 introduces
