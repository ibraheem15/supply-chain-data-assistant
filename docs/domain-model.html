Current State

src/data/ contains two Python modules and two SQL scripts, and src/resources/ holds the agent's tools (Phase 3c, complete), and src/agent/ holds the orchestrator (Phase 4a): ingest_supply_chain_dataset.py (Phase 1, complete), ingest_sop_pinecone.py (Phase 3a, complete: parsing, chunking, embedding, incremental sync), and setup_security_and_view.sql (Phase 3b, complete). The agent orchestration that picks between the tools is not built yet — see the last section below.

Phase 3b: Agent Security Layer (SQL)

setup_security_and_view.sql is a SQL script, not Python, so there are no classes to diagram. What it creates inside SupplyChainDb (the rewrite uses USR_FDE_RO_2 and the schema ai_2):

ObjectRole
dbo.supply_chain_logisticsReal table with legacy column names; written only by the Phase 1 loader
ai_2.VW_SUPPLY_CHAIN_READINGSView over that table, columns renamed to the ubiquitous-language names
USR_FDE_RO_2 (login + user)The agent's identity: SELECT on the view only, everything else denied

Dependency direction: USR_FDE_RO_2 → ai_2.VW_SUPPLY_CHAIN_READINGS → dbo.supply_chain_logistics. The user has no path to the table except through the view (ownership chaining).

ConceptWhere
Anti-Corruption LayerThe view is the outbound counterpart of LEGACY_COLUMN_NAMES: the loader translates names in, the view translates them out. The mapping exists in both places and must be kept in sync
Least privilegeGRANT SELECT on one object; DENY on the dbo and ai_2 schemas overrides any grant
Login vs userThe login (server level, in master) proves who the agent is; the user (database level) holds its permissions
Packages as layersSchema ai_2 is the agent-facing layer, dbo the legacy layer

Phase 3c: Agent Tools (src/resources/)

The application layer. Each tool is a plain function returning {"status": "ok" | "error", ...}; mcp_server.py is a thin wrapper that registers them over stdio. Dependencies: agent (Phase 4) → mcp_server.py → three tools. query_telemetry_data connects as USR_FDE_RO_2 to ai_2.VW_SUPPLY_CHAIN_READINGS through db.py (string validation, 50 row cap, 15s timeout); fetch_weather_conditions calls the Open-Meteo REST API (10s timeout); search_compliance_sop embeds the question with the same local model used at indexing time and queries Pinecone. settings.py loads the env files and schema_context.py supplies column docs and a legacy glossary to the server.

ConceptWhere
Interface as ContractThe shared result shape: expected failures are data the agent can act on, never exceptions. unavailable (service down) is not yet separated from error
Defence in depthvalidate_sql() and the row cap sit on top of the Phase 3b database permissions
Dependency directionTools depend on stores (SQL Server, Pinecone, HTTP); nothing in src/data/ depends on tools. sop_tool imports the embedding model name from data/ so query and index embeddings cannot diverge
Ubiquitous Languageschema_context.py generates the legacy-to-business glossary from LEGACY_COLUMN_NAMES, so the SOP's legacy names resolve to the names the agent can query
Packages as layersresources/ is the application layer between the agent and the data layer

Phase 4a: Agent Orchestrator (src/agent/)

A LangGraph ReAct agent. graph.py is pure wiring (the LLM and tools are arguments); llm.py builds the Gemini or Groq chat model, tools.py describes how to start mcp_server.py (a StdioTransport) and opens it with LangChain's MCPAdapter, prompts.py holds the system prompt, and cli.py is the terminal chat, which keeps one MCP session open for the whole conversation. Server and client both use FastMCP. Graph: START → Reasoner (LLM + system prompt); after the Reasoner, a tool call goes to Tools (ToolNode over MCP), which returns to the Reasoner, and no tool call goes to END.

ConceptWhere
Dependency directionagent/ depends on resources/ only through MCP; resources/ knows nothing about the agent. graph.py depends on no I/O: the model and the tools are arguments, so it can be tested with a scripted fake LLM (tests not yet written in the rewrite)
Interface as ContractThe agent sees three MCP tools and their descriptions, never the Python functions or the database
State as the single source of truthThe message list is the graph state; the checkpointer (MemorySaver, one thread_id per chat) gives conversation memory
Packages as layersagent/ is the orchestration layer above resources/ (application layer) above data/

Phase 5: Audit Log (src/agent/audit.py, turn.py) and UI (src/ui/)

run_turn() runs one question through the graph (astream, one update per node) and yields typed TurnEvents; it also writes one audit row per event through audit.record(), which runs the insert in a worker thread, redacts secrets and never raises. The CLI and the UI both consume run_turn(), so neither can skip the audit. Flow: cli.py or ui/app.py (via ui/runtime.py, a background thread with its own event loop) → run_turn() → graph.py; run_turn() → record() (USR_FDE_AUDIT_W_2, INSERT only) → audit_2.AgentAuditLog → AuditReader (USR_FDE_AUDIT_R_2, SELECT only) → the audit tab. The agent's own SQL login USR_FDE_RO_2 is denied on the whole audit_2 schema. ui/runtime.py and ui/app.py were adapted from the reference implementation, not written by hand.

ConceptWhere
Least privilege, separation of dutiesThree logins: the agent acts (read-only on data, denied on audit), the writer records (INSERT only), the reader views (SELECT only)
Fail open, but loudlyrecord() never raises: a failed write returns False, the turn yields one audit_warning, and the agent carries on
One code pathrun_turn() is the only place a turn runs and is audited; graph.py stays free of I/O
Dependency directionui/ depends on agent/; agent/ does not know the UI exists. resources/db.py is shared by the SQL tool and the audit code
Packages as layersui/ (presentation) over agent/ (orchestration) over resources/ (tools) over data/

Accepted Limits and Open Items

Known limits (see phase5-notes.md): one user at a time, no login, a failed audit write is lost apart from the warning, and the database owner can edit the audit table. Still open in the rewrite: tests for src/agent/ and src/ui/, and the weather and SOP tools do not return an unavailable status yet.
